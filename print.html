W2POSIX fundamentals: the shellPOSIX 基础：Shell

  • The shell expands before running: word splitting, globs, $var, $( ). Quote "$var".
  • Globs that match nothing stay literal; \*, '*', "*" all pass a literal *.
  • x=5 (no spaces); VAR=v cmd sets VAR only in cmd's environment; $x in the same line is expanded before.
  • fd 0/1/2; | > >> < 2> 2>&1 <<< <<EOF; diff tmp <(ls -l).
  • Filters: cat head tail sort uniq wc tr cut; uniq only removes *adjacent* duplicates → sort | uniq.
  • Scripts: #!/bin/sh / #!/usr/bin/env bash, chmod +x, $0 $1 $# $@ $?, test/[ ]/[[ ]], && ||.
  • set -e -u -o pipefail; PATH lookup = first match wins; never put . on PATH.
  • Jobs: &, Ctrl-Z, fg, bg, jobs, wait, Ctrl-C, Ctrl-D, kill.
  • Permission rules: need x on every directory of the path; setuid (chmod u+s, -rwsr-xr-x); visudo.
  • shell 在执行之前展开：分词、通配符、$var、$( )。变量要写成 "$var"。
  • 无匹配的通配符原样保留；\*、'*'、"*" 都能传入字面 *。
  • x=5（等号两边无空格）；VAR=v cmd 只对 cmd 的环境生效；同一行里的 $x 已被提前展开。
  • 文件描述符 0/1/2；| > >> < 2> 2>&1 <<< <<EOF；diff tmp <(ls -l)。
  • 过滤器：cat head tail sort uniq wc tr cut；uniq 只去掉相邻重复行 → 先 sort 再 uniq。
  • 脚本：#!/bin/sh / #!/usr/bin/env bash，chmod +x，$0 $1 $# $@ $?，test/[ ]/[[ ]]，&& ||。
  • set -e -u -o pipefail；PATH 查找取第一个匹配；不要把 . 加进 PATH。
  • 作业：&、Ctrl-Z、fg、bg、jobs、wait、Ctrl-C、Ctrl-D、kill。
  • 权限：路径上每一级目录都要有 x；setuid（chmod u+s → -rwsr-xr-x）；用 visudo 改 sudoers。

  • Matching is left-to-right with backtracking and greedy.
  • grep -i -v -o -c -w -R -E -P; grep -c counts lines, grep -o … | wc -l counts matches.
  • sed 's/re/rep/g', &, \1, -n + p, -i in place, y/abc/xyz/.
  • awk -F, '/re/ { … } END { … }', $0 $1 NF, $2 ~ /re/.

W4Version control with GitGit 版本控制

  • Core loop: init → edit → add → commit → status/log.
  • git diff (working tree vs last commit), git diff HASH; git restore f, git restore -s HASH f.
  • checkout HASH = detached HEAD (moves *you*); restore changes *files*.
  • revert adds an inverse commit (safe when shared); reset moves the branch back (rewrites; --hard also changes files).
  • branch / switch / merge / branch -d.
  • .gitignore for build outputs; Git ≠ GitHub; clone, remote add origin, pull = fetch + merge, push rejected if remote has commits you lack.
  • 核心循环：init → 修改 → add → commit → status/log。
  • git diff（工作区 vs 最新提交）、git diff HASH；git restore f、git restore -s HASH f。
  • checkout HASH 进入分离 HEAD（移动的是“你所在的时间点”）；restore 只改文件。
  • revert 新增一个反向提交（共享后也安全）；reset 把分支指针移回（改写历史，--hard 连文件一起改）。
  • branch / switch / merge / branch -d。
  • 编译产物放进 .gitignore；Git ≠ GitHub；clone、remote add origin、pull = fetch + merge；远程有你没有的提交时 push 会被拒绝。

W5Collaborating with GitGit 协作

  • Conflict markers <<<<<<< HEAD / ======= / >>>>>>> branch; edit → git add → git commit.
  • Shared access: pull before push; fetch then decide. Don't push broken code.
  • No access: fork → push to fork → pull request → maintainer reviews and merges. Patches: format-patch, apply, am.
  • git rebase main replays your commits on top; conflicts → add + rebase --continue / --abort / --skip.
  • rebase --onto, rebase -i (pick, reword, edit, squash, drop); pull.rebase true.
  • Rebase rewrites commit IDs: don't rebase what others already have (or you must force-push).
  • 冲突标记 <<<<<<< HEAD / ======= / >>>>>>> 分支名；手动编辑 → git add → git commit。
  • 共享权限：先 pull 再 push；也可先 fetch 再决定。别推送坏代码。
  • 无权限：fork → 推到自己的 fork → 发 pull request → 维护者审核合并。补丁：format-patch、apply、am。
  • git rebase main 把你的提交“重放”到最新 main 之上；冲突时 add + rebase --continue / --abort / --skip。
  • rebase --onto、rebase -i（pick、reword、edit、squash、drop）；pull.rebase true。
  • rebase 会生成新的提交 ID：别 rebase 别人已经拿到的历史（否则只能强推）。

W6Testing测试

  • Testing asks: for all valid inputs, is the output the intended one? Most bugs = unclear spec.
  • assert() checks internal assumptions at runtime; -DNDEBUG compiles them out.
  • Unit test = call an interface with an input, compare with expected output. Regression = a test that used to pass now fails.
  • Unity: setUp, tearDown, TEST_ASSERT_EQUAL, UNITY_BEGIN / RUN_TEST / UNITY_END; link with -l unity.
  • TDD: RED (write failing test) → GREEN (simplest passing code) → REFACTOR (clean up, all tests pass).
  • Property testing (QuickCheck), fuzzing (AFL), formal verification (Lean).
  • Pre-commit hook: non-zero exit aborts the commit; --no-verify skips. GitHub Actions: .github/workflows/*.yml, on: push.
  • 测试的问题：对所有合法输入，输出是否符合预期？多数 bug 来自规格不清。
  • assert() 在运行时检查内部假设；-DNDEBUG 会把断言编译掉。
  • 单元测试 = 用某输入调用接口，与期望输出比较。回归 = 以前能通过的测试现在失败。
  • Unity：setUp、tearDown、TEST_ASSERT_EQUAL、UNITY_BEGIN / RUN_TEST / UNITY_END；链接 -l unity。
  • TDD：红（先写会失败的测试）→ 绿（最简单的实现让它通过）→ 重构（整理代码，所有测试仍通过）。
  • 属性测试（QuickCheck）、模糊测试（AFL）、形式化验证（Lean）。
  • pre-commit 钩子：返回非零就中止提交；--no-verify 跳过。GitHub Actions：.github/workflows/*.yml，on: push。

W7Debugging调试

  • Testing says *that* something is wrong; debugging finds *why*.
  • strace cmd, strace -e openat cmd, strace -p PID; ltrace for library calls.
  • valgrind --leak-check=yes ./prog: invalid read/write, definitely / indirectly / possibly lost, still reachable.
  • Compile with -g -O0. gdb: run (r), break/b, step/s (into calls), next/n (over calls), stepi/si, continue/c, print/p, set var, info functions, info registers, disas, list, jump.
  • Crackme toolkit: strings, ltrace, objdump -d, gdb.
  • 测试告诉你“有错”；调试找出“为什么错”。
  • strace cmd、strace -e openat cmd、strace -p PID；ltrace 看库函数调用。
  • valgrind --leak-check=yes ./prog：非法读写；definitely / indirectly / possibly lost、still reachable 的区别。
  • 用 -g -O0 编译。gdb：run(r)、break/b、step/s（进入函数）、next/n（跳过函数）、stepi/si、continue/c、print/p、set var、info functions、info registers、disas、list、jump。
  • crackme 工具箱：strings、ltrace、objdump -d、gdb。

W8Relational databases: design关系数据库：设计

  • ACID = Atomic, Consistent, Isolated, Durable.
  • Entity → table, attribute → column, record → row; relationships via foreign keys.
  • Keys: candidate (minimal unique set), composite (>1 attribute), surrogate (invented ID), primary (chosen), foreign (another table's PK).
  • X → Y: each X has at most one Y. Partial dependency (on part of a composite key) and transitive dependency (X→Y→Z).
  • 1NF atomic values; 2NF no partial deps; 3NF no transitive deps; BCNF every determinant is a candidate key.
  • CREATE TABLE … PRIMARY KEY … FOREIGN KEY(x) REFERENCES t(y); PRAGMA foreign_keys = ON;; create referenced table first, drop in reverse order.
  • ACID = 原子性、一致性、隔离性、持久性。
  • 实体 → 表，属性 → 列，记录 → 行；联系通过外键表示。
  • 键：候选键（最小唯一属性集）、复合键（多于一个属性）、代理键（人为编号）、主键（选定的）、外键（引用另一表的主键）。
  • X → Y：每个 X 最多对应一个 Y。部分依赖（依赖复合键的一部分）与传递依赖（X→Y→Z）。
  • 1NF 值原子；2NF 无部分依赖；3NF 无传递依赖；BCNF 每个决定因素都是候选键。
  • CREATE TABLE … PRIMARY KEY … FOREIGN KEY(x) REFERENCES t(y)；PRAGMA foreign_keys = ON;；先建被引用表，删除时顺序相反。

W9Relational databases: queries关系数据库：查询

  • SQLite affinities: INTEGER, TEXT, BLOB, REAL, NUMERIC (+ NULL). Lengths like VARCHAR(10) are ignored → use CHECK.
  • SELECT … FROM … WHERE … GROUP BY … HAVING … ORDER BY … LIMIT … (write order).
  • WHERE filters rows before grouping; HAVING filters groups after.
  • count avg sum min max; LIKE '%x%', IN (…), IS NULL.
  • INNER (matches only), LEFT / RIGHT / FULL OUTER (keep unmatched side, fill NULL), CROSS (Cartesian product).
  • Sub-query as a temporary table: FROM (SELECT …).
  • UPDATE … SET … WHERE, ALTER TABLE, upsert ON CONFLICT … DO UPDATE, BEGIN TRANSACTION … END TRANSACTION.
  • SQLite 亲和类型：INTEGER、TEXT、BLOB、REAL、NUMERIC（以及 NULL）。VARCHAR(10) 这类长度会被忽略 → 用 CHECK。
  • 书写顺序：SELECT … FROM … WHERE … GROUP BY … HAVING … ORDER BY … LIMIT …。
  • WHERE 在分组前过滤行；HAVING 在分组后过滤组。
  • count avg sum min max；LIKE '%x%'、IN (…)、IS NULL。
  • INNER（只保留匹配）、LEFT / RIGHT / FULL OUTER（保留未匹配一侧并补 NULL）、CROSS（笛卡尔积）。
  • 子查询当作临时表：FROM (SELECT …)。
  • UPDATE … SET … WHERE、ALTER TABLE、upsert ON CONFLICT … DO UPDATE、BEGIN TRANSACTION … END TRANSACTION。

W10Databases beyond SQL: Datalog超越 SQL：Datalog

  • Building SQL with sprintf + user input → SQL injection (1 OR 1=1). Fix: prepared statements (? + bind).
  • Self-join finds one level up; an unknown depth needs recursion (WITH RECURSIVE in SQL, or Datalog).
  • Datalog: atoms lowercase, variables Uppercase/_, facts p(a)., rules head :- b1, b2. (comma = AND, several rules = OR), queries ?- p(X).
  • Recursive rule: ancestor(X,Y) :- parent(X,Z), ancestor(Z,Y). plus a base case.
  • X != Y to exclude self (e.g. siblings).
  • Access control in Datalog: DAC, delegation, roles, MAC (Bell–LaPadula: no read up / no write down; Biba: the reverse).
  • 用 sprintf 拼接用户输入构造 SQL → SQL 注入（1 OR 1=1）。修复：预编译语句（? 占位 + 绑定）。
  • 自连接只能往上找一层；层数未知要用递归（SQL 的 WITH RECURSIVE，或 Datalog）。
  • Datalog：原子小写，变量大写或 _ 开头，事实 p(a).，规则 head :- b1, b2.（逗号 = 且，多条规则 = 或），查询 ?- p(X).
  • 递归规则：ancestor(X,Y) :- parent(X,Z), ancestor(Z,Y).，外加一条基础规则。
  • 用 X != Y 排除自己（如兄弟姐妹）。
  • 用 Datalog 做访问控制：DAC、委托、角色、MAC（Bell–LaPadula：不上读、不下写；Biba：相反）。

1.1.1Shell & terminalShell 与终端★
  • Terminal: the window/device that shows text and takes keystrokes. Shell: the program in it that reads your command line and runs programs (bash on most Linux, zsh on macOS).
  • Prompt: the shell is waiting for input. bash shows $, zsh %, root #. Prompts can be customised to show user, host, directory.
  • One of the oldest interfaces; awkward at first, very powerful once learnt. The trick: use it every day.
  • Output is text; most terminals can't show pictures (some can: kitty graphics protocol, sixels).
  • 终端（terminal）：显示文字、接收按键的窗口/设备。Shell：运行在终端里、读取命令行并启动程序的程序（多数 Linux 是 bash，macOS 是 zsh）。
  • 提示符（prompt）：表示 shell 正在等待输入。bash 用 $，zsh 用 %，root 常用 #。提示符可自定义显示用户、主机、目录。
  • 最古老的交互方式之一；一开始别扭，熟练后非常强大。诀窍：每天用。
  • 输出是文本；大多数终端不能显示图片（少数可以：kitty 图形协议、sixel）。

1.2.1SSH: client & daemonSSH：客户端与守护进程★

1.2.2Host key verification主机密钥校验★
  • First connection to a new host: "authenticity of host can't be established… fingerprint SHA256:… Are you sure?" Answer yes → host's public key stored in ~/.ssh/known_hosts.
  • Later connections compare against known_hosts; a changed key triggers a warning (possible attack).
  • To verify properly, have someone with physical access run ssh-keyscan -q -t ed25519 localhost on the server and compare fingerprints.
  • Purpose: defeat Man-in-the-middle attack attacks.
  • 首次连接新主机会问：“无法确认主机真实性……指纹 SHA256:…… 是否继续？”回答 yes → 主机公钥写入 ~/.ssh/known_hosts。
  • 以后每次连接都与 known_hosts 比较；密钥变化会报警（可能遭到攻击）。
  • 严格校验：让能物理接触服务器的人在服务器上运行 ssh-keyscan -q -t ed25519 localhost，对比指纹。
  • 目的：防御中间人攻击。
1.2.3Man-in-the-middle attack中间人攻击
  • Attacker (Smith) tricks the client (Evelyn) into connecting to them instead of the real server (iMac).
  • Smith relays everything both ways, so it looks normal — but can record and modify traffic.
  • Defence in SSH: check the server's host key fingerprint (Host key verification); key-based auth never sends a reusable secret (SSH key pairs).
  • 攻击者（Smith）诱使客户端（Evelyn）连到自己，而不是真正的服务器（iMac）。
  • Smith 双向转发所有内容，看起来一切正常——但可以记录甚至篡改通信。
  • SSH 中的防御：核对服务器主机密钥指纹（主机密钥校验）；密钥认证不会发送可重复使用的秘密（SSH 密钥对）。

1.2.5SSH key pairsSSH 密钥对★
  • Generate: ssh-keygen -t ed25519 (modern, secure algorithm). Default location ~/.ssh/. Empty passphrase = convenient; passphrase = 2FA.
  • Private key id_ed25519: never leaves your machine. Public key id_ed25519.pub: give to every server/service (lab, GitHub).
  • How login works: server sends a random challenge; client signs it with the private key; server checks the signature with the stored public key. The key itself is never sent → a breached service can't impersonate you elsewhere.
  • Install on a server: append the public key to ~/.ssh/authorized_keys (one key per line) and chmod 600 it.
  • Reusing one public key everywhere is safe security-wise but lets services link your identities (privacy). Use -i FILE or IdentityFile for different keys.
  • If you overwrite an existing key you break whatever used it → answer n to "Overwrite?".
  • 生成：ssh-keygen -t ed25519（现代、安全的算法）。默认存放在 ~/.ssh/。不设口令 = 方便；设口令 = 双因素。
  • 私钥 id_ed25519：永不离开你的机器。公钥 id_ed25519.pub：交给每台服务器/服务（实验室、GitHub）。
  • 登录原理：服务器发送随机挑战值；客户端用私钥对其签名；服务器用存储的公钥验证签名。密钥本身从不发送 → 某个服务被攻破也无法拿你的身份登录别处。
  • 部署到服务器：把公钥追加到 ~/.ssh/authorized_keys（每行一个），再 chmod 600。
  • 各处共用一个公钥在安全上没问题，但服务之间可据此关联你的身份（隐私问题）。不同用途可用 -i 文件 或 IdentityFile 指定不同密钥。

  • UNIX design principle: almost every interaction with the OS looks like reading/writing a file: devices in /dev, processes in /proc, kernel state in /sys.

1.6.2UNIX DAC: rwx permissionsUNIX 自主访问控制：rwx 权限★
  • DAC (discretionary access control): the owner decides. Permission to read, write, execute is set separately for user (owner), group, other.
  • ls -l mode string: type + 3 triplets. -rwxr-x--- root wheel script.sh: owner rwx, group r-x, others nothing → a wheel member can read and run but not write.
  • Octal: r=4, w=2, x=1. rwx=7, r-x=5, rw-=6, r--=4, ---=0. So 750 = rwxr-x---, 600 = rw-------, 644 = rw-r--r--.
  • chmod changes mode (chmod 600 f, chmod u+x f, chmod go-rwx d); chown changes owner (and group: chown user:group f); chgrp changes group.
  • Directories: r = list contents; x = enter (cd) / access files inside; w = create/delete entries.
  • Access needs permission along the whole path (Permission along the whole path).
  • DAC（自主访问控制）：由属主决定。读 r、写 w、执行 x 分别对属主（user）、属组（group）、其他人（other）设置。
  • ls -l 的权限串：类型 + 三组三位。-rwxr-x--- root wheel script.sh：属主 rwx，属组 r-x，其他人无 → wheel 组成员可读可执行、不可写。
  • 八进制：r=4，w=2，x=1。rwx=7，r-x=5，rw-=6，r--=4，---=0。故 750 = rwxr-x---，600 = rw-------，644 = rw-r--r--。
  • chmod 改权限（chmod 600 f、chmod u+x f、chmod go-rwx d）；chown 改属主（也可改组：chown 用户:组 f）；chgrp 改属组。
  • 目录：r = 列出内容；x = 进入（cd）/访问其中文件；w = 创建/删除条目。
  • 访问需要整条路径上的权限（整条路径的权限）。

2.2.1Shell expansion orderShell 展开顺序★
  • The shell, not the program, rewrites your line before running it. Roughly: ~ and variables $x → command substitution $( ) → word splitting on whitespace → glob (pathname) expansion → quote removal → run with argv.
  • The program only sees the final list of arguments (argv[0] = program name).
  • Lab tool arguments.c prints each argument in brackets — the best way to see what the shell did.
  • 改写命令行的是 shell，不是程序，并且发生在执行之前。大致顺序：~ 与变量 $x → 命令替换 $( ) → 按空白分词 → 通配符（路径名）展开 → 去掉引号 → 以 argv 形式运行。
  • 程序只看到最终的参数列表（argv[0] = 程序名）。
  • 实验工具 arguments.c 用方括号打印每个参数——最直观地看出 shell 做了什么。
#include <stdio.h>
int main(int argc, char** argv) {
  for (int i = 0; i < argc; i++)
    printf("Argument #%i: [%s]\n", i, argv[i]);
  return 0;

2.2.2Whitespace & word splitting空白与分词★
  • Unquoted whitespace separates arguments; runs of spaces count as one separator: ./arguments one two → 2 args.

2.4.1Loops, tests & exit status循环、条件与退出状态★

  • 练习点：位置参数、case、字符串截取 ${1%.c}、-f 测试、&&、退出码。真实项目用make完成这类工作。

[ $# -eq 2 ] || usage

            gcc -Wall -std=c11 -g "$name.c" -o "$name"; }
run()     { [ -x "$name" ] || { echo "no ./$name" >&2; exit 3; }; "./$name"; }
case "$1" in
  compile) compile ;;
  run)     run ;;
  build)   compile && run ;;
  *)       usage ;;

3.1What regular expressions are正则表达式是什么

3.1.1Regular expressions正则表达式★
  • A language for matching text, based on a finite state machine. Also called re / regex / regexp.
  • Described by Stephen Cole Kleene in the 1950s; built into UNIX tools before standards existed.
  • A regular language: bounded complexity, no arbitrary recursion/nesting (can't match balanced brackets).
  • Finicky and brittle, "write-only code" (you will forget how it works) — but solves ~99% of practical text problems. Example of excess: the "almost works" email-address regex.
  • 一种匹配文本的语言，基于有限状态机。也写作 re / regex / regexp。
  • 由 Stephen Cole Kleene 于 1950 年代提出；在标准出现前就已内置于 UNIX 工具。
  • 属于正则语言：复杂度有上限，不能任意递归/嵌套（无法匹配成对括号）。
  • 挑剔、脆弱，“只写代码”（写完你自己也会忘）——但能解决约 99% 的实际文本问题。反面教材：那个“几乎能用”的邮箱正则。

3.1.3How a regex is matched正则如何匹配
  • Start at the left, one item at a time: if it matches, continue; otherwise backtrack and retry (possibly from the next character).
  • Most regexes are greedy: quantifiers match as much as possible (a.*b on axbxb matches the whole string).
  • A regex with no anchors matches if it occurs anywhere in the line (substring).
  • 从左边开始逐项匹配：匹配就继续；否则回溯重试（可能从下一个字符开始）。
  • 大多数正则是贪婪的：量词尽可能多地匹配（a.*b 在 axbxb 上匹配整个字符串）。
  • 没有锚点的正则只要在行中任意位置出现就算匹配（子串）。

3.6Perl & the UNIX philosophyPerl 与 UNIX 哲学

3.6.1UNIX philosophyUNIX 哲学
  • Write small tools that do one thing well, and connect them with text streams (Pipes |).
  • shell, grep, sed, awk exist separately because they were "written in anger" for a specific job.
  • Downside: 12 tools = 12 syntaxes to remember → motivation for Perl & Raku.

  • shell、grep、sed、awk 各自独立，是因为它们都是为了解决某个具体问题“一气之下”写出来的。

  • 通用编程语言，内置大量文本处理功能（PCRE 正则）；可视为更稳定、更可移植的 shell 脚本。

4.3Using history: compare & undo利用历史：比较与撤销

4.3.1git diffgit diff 比较差异★
  • git diff = working tree vs last commit (what you haven't committed). git diff HASH = now vs that commit. git diff HASH file for one file. git diff --staged = staged vs last commit.
  • Output: - lines removed, + lines added, @@ hunk headers with line numbers.
  • git diff = 工作区 vs 最新提交（还没提交的改动）。git diff HASH = 当前 vs 某次提交。git diff HASH 文件 只看一个文件。git diff --staged = 暂存区 vs 最新提交。
  • 输出：- 删除的行，+ 新增的行，@@ 是带行号的块头。
4.3.2git restoregit restore 恢复文件★
  • git restore FILE discards uncommitted changes: file back to the last committed version.
  • git restore -s HASH FILE sets your working copy of FILE to its version at HASH. git status then shows FILE as modified — you changed the file, not *where* you are in history.
  • git restore --staged FILE unstages.
  • git restore 文件 丢弃未提交的修改：文件恢复为最近一次提交的版本。
  • git restore -s HASH 文件 把文件的工作副本设为它在 HASH 时的版本。此后 git status 显示该文件已修改——你改的是文件，而不是你在历史中的*位置*。
  • git restore --staged 文件 取消暂存。
4.3.3git checkout & detached HEADgit checkout 与分离 HEAD★
  • HEAD = pointer to "where you are": normally the tip of the current branch.
  • git checkout HASH = time travel: the whole working tree becomes that commit and HEAD points at it directly → detached HEAD. git status says "working tree clean" (files match where HEAD is).
  • Back to the future: git checkout main (or master) re-attaches HEAD.
  • restore vs checkout: restore changes file contents; checkout changes Git's notion of when you are. Watch out for losing uncommitted changes.
  • HEAD = 指向“你现在在哪”的指针：通常是当前分支的最新提交。
  • git checkout HASH = 时间旅行：整个工作区变成那次提交，HEAD 直接指向它 → 分离 HEAD（detached HEAD）。git status 显示 “working tree clean”（文件与 HEAD 所在位置一致）。
  • 回到未来：git checkout main（或 master）让 HEAD 重新挂回分支。
  • restore 与 checkout：restore 改文件内容；checkout 改变 Git 认为你处于哪个时间点。注意别丢了未提交的修改。

  • Reverting is not enough once pushed: the secret stays in history. You'd need to rewrite history and force push — and still treat any password as compromised: change it at once.

4.4Branches分支

4.4.1Branches分支★
  • Parallel timelines. Default branch master or main (name doesn't matter, be consistent; you can rename/configure it).
  • git branch NAME creates; git branch lists (current marked *); git switch NAME moves to it (older: git checkout NAME).
  • New commits go on the current branch; logs diverge after the branch point. Switching changes files (a README added on docs disappears on main).
  • Use: try something / develop a feature without breaking working code. A well-regulated repo: every change to main arrives as a merge from a feature branch.
  • Delete: git branch -d NAME (merged), git branch -D NAME (force, unmerged work lost).
  • 平行时间线。默认分支 master 或 main（名字无所谓，保持一致；可改名或配置）。
  • git branch 名字 创建；git branch 列出（当前分支带 *）；git switch 名字 切换（旧写法：git checkout 名字）。
  • 新提交加在当前分支上；分叉点之后各分支日志不同。切换分支会改变文件（在 docs 上新增的 README 回到 main 就不见了）。
  • 用途：尝试新想法 / 开发新功能而不破坏可用代码。规范的仓库：main 上的每次变更都来自功能分支的合并。
  • 删除：git branch -d 名字（已合并），git branch -D 名字（强制，未合并的工作会丢失）。

4.4.2git mergegit merge 合并★
  • git merge BRANCH brings BRANCH's commits into the current branch.
  • If the timelines don't conflict (no same lines edited differently), Git merges automatically, creating a merge commit with two parents (editor opens with "Merge branch 'docs'"). Both edits survive; git log now includes the other branch's commits.
  • If one side has no new commits, Git just moves the pointer (fast-forward).
  • When both changed the same lines → Merge conflicts.
  • git merge 分支 把该分支的提交合并进当前分支。
  • 若两条时间线不冲突（没有对同一行做不同修改），Git 自动合并，生成一个有两个父提交的合并提交（编辑器预填 “Merge branch 'docs'”）。两边的修改都保留；git log 中出现另一分支的提交。
  • 若其中一方没有新提交，Git 只需移动指针（快进 fast-forward）。
  • 双方改了同一行 → 合并冲突。

5.1Merge conflicts合并冲突

5.1.1Merge conflicts合并冲突★
  • Happen when two branches changed the same lines differently. Git merges everything else and stops: "CONFLICT (content): Merge conflict in webcode.c … fix conflicts and then commit the result."
  • Read the output. Affected files are listed in git status. Ignore it and your code stops working.
  • Markers in the file: <<<<<<< HEAD (your current branch's version) / ======= / >>>>>>> comments (the incoming branch's version).
  • Resolve: edit to the correct final text (one side, the other, or a combination — e.g. keep xrealloc *and* the line break), remove the markers, git add each file, git commit explaining the resolution.
  • Can be several conflict points per file and several files. Careless merging loses functionality — you must understand both versions.
  • Same markers appear in git pull and git rebase (git rebase).
  • 两个分支对同一行做了不同修改时发生。Git 合并其余部分后停下：“CONFLICT (content): Merge conflict in webcode.c … fix conflicts and then commit the result.”
  • 读输出。受影响的文件会列在 git status 中。置之不理，代码就跑不了。
  • 文件中的标记：<<<<<<< HEAD（当前分支的版本）/ ======= / >>>>>>> comments（被合并进来的分支的版本）。
  • 解决：把内容改成正确的最终版本（取一边、另一边或组合——例如保留 xrealloc *并且*保留换行），删掉标记，对每个文件 git add，再 git commit 说明如何解决。
  • 一个文件可能有多处冲突，也可能多个文件冲突。合并不谨慎会丢功能——必须理解两个版本。
  • git pull 和 git rebase 中出现的是同样的标记（git rebase 变基）。

5.2Collaborating with shared access有共享权限的协作

5.2.1Shared-access workflow共享权限工作流★
  • Everyone has push rights to one remote; everyone git clones it, works and commits locally.
  • Sync: git pull then git push. Rejected push → pull, resolve, push. Conflicts are common here.
  • pull = fetch + merge: you can git fetch first, inspect, then decide (merge or rebase).
  • Etiquette: never push broken code. Team order matters: whoever pushes second resolves the conflict.
  • 所有人对同一个远程有推送权限；每人 git clone，在本地工作和提交。
  • 同步：先 git pull 再 git push。推送被拒 → pull、解决冲突、再 push。这种模式下冲突很常见。
  • pull = fetch + merge：可以先 git fetch，看清楚，再决定合并还是 rebase。
  • 礼仪：永远别推送坏代码。顺序很重要：后推送的人负责解决冲突。
5.2.2develop & feature branchesdevelop 与功能分支
  • Keep main stable; integrate on a shared develop branch; each person works on their own feature branch.
  • Publish a branch: git push --set-upstream origin NAME (then plain git push). See remote branches: git branch -a.
  • Finish a feature: commit → git fetch → git switch develop → git pull if behind → git merge NAME → resolve → git push.
  • If develop moved on, rebase the feature onto it first (git rebase develop), which then needs a force push of the feature branch (Force push).
  • 保持 main 稳定；在共享的 develop 分支上集成；每人在自己的功能分支上开发。
  • 发布分支：git push --set-upstream origin 名字（之后直接 git push）。查看远程分支：git branch -a。
  • 完成功能：提交 → git fetch → git switch develop → 落后就 git pull → git merge 名字 → 解决冲突 → git push。
  • 若 develop 已前进，先把功能分支 rebase 到它上面（git rebase develop），之后功能分支需要强制推送（强制推送）。

5.3Collaborating without access无权限的协作

5.3.1Forks & pull requestsFork 与 Pull Request★
  • For many collaborators (most open source) you don't hand out write access.
  • Contributor forks (public copy under their account) → clones the fork → pushes commits to the fork → opens a pull request asking the owner to pull them.
  • Owner reviews (discussion, requested changes), then merges — or ignores/declines. Maintainers needn't watch forks until a PR arrives.
  • Side benefit: if a project is abandoned or refuses something, the community can adopt a fork as canonical.
  • 协作者众多（大多数开源项目）时，不会给每个人写权限。
  • 贡献者 fork（在自己账号下的公开副本）→ 克隆 fork → 把提交推到 fork → 发起 pull request，请所有者拉取。
  • 所有者审核（讨论、要求修改）后合并——或者忽略/拒绝。维护者在收到 PR 之前无需关心各个 fork。
  • 附带好处：项目被放弃或拒绝某些改动时，社区可以把某个 fork 当作正统。
5.3.2Patches: format-patch, apply, am补丁：format-patch、apply、am
  • Old-school distributed development (e.g. email, private server without PR UI).
  • Contributor: git fetch then git format-patch origin/main → patch file(s) describing how your commits differ from the remote.
  • Owner: git apply PATCH only changes the working tree (review, then commit); git am PATCH applies it directly as a commit (keeps author & message).
  • 传统的分布式开发方式（如通过邮件、没有 PR 界面的私有服务器）。
  • 贡献者：git fetch 后 git format-patch origin/main → 生成补丁文件，描述你的提交与远程的差异。
  • 所有者：git apply 补丁 只修改工作区（审核后再提交）；git am 补丁 直接作为提交应用（保留作者和说明）。

5.4Rewriting history: rebase改写历史：rebase

5.4.1git rebasegit rebase 变基★
  • "Editing the historical record" — common cause of catastrophic repo problems.
  • Use: a branch split from main at B; main moved on to D. git switch branch; git rebase main → Git finds the branch's commits missing from main, resets to main's tip, and replays them on top: the branch now appears to split from D.
  • Conflicts appear one commit at a time with the usual markers; fix → git add FILES → git rebase --continue (you may edit the message). No merge commit.
  • git rebase --abort gives up entirely; git rebase --skip throws away the current commit's changes (dangerous).
  • Replayed commits are new commits with new IDs → don't rebase history others already have.
  • “篡改历史记录”——仓库灾难的常见原因。
  • 用途：分支在 B 处从 main 分出；main 已前进到 D。git switch branch; git rebase main → Git 找出分支上 main 没有的提交，先回到 main 的最新提交，再把它们逐个重放上去：看起来分支是从 D 分出的。
  • 冲突逐个提交出现，标记相同；修好 → git add 文件 → git rebase --continue（可修改说明）。不产生合并提交。
  • git rebase --abort 彻底放弃；git rebase --skip 丢弃当前这个提交的改动（危险）。
  • 重放的提交是新提交、ID 也是新的 → 别 rebase 别人已经拿到的历史。

5.4.2rebase --ontorebase --onto
  • git rebase --onto NEWBASE OLDBASE BRANCH transplants the commits after OLDBASE (up to BRANCH) onto NEWBASE: e.g. git rebase --onto master branch subbranch.
  • Delete commits from history: git rebase --onto master~5 master~3 master turns A-B-C-D-E-F into A-D-E-F (drops B, C).
  • vs git revert: revert keeps history and adds undo commits; --onto makes the commits never have existed.
  • git rebase --onto 新基点 旧基点 分支 把旧基点之后（到该分支为止）的提交移植到新基点上：如 git rebase --onto master branch subbranch。
  • 从历史中删除提交：git rebase --onto master~5 master~3 master 把 A-B-C-D-E-F 变成 A-D-E-F（删掉 B、C）。
  • 与 git revert 对比：revert 保留历史并新增撤销提交；--onto 让那些提交像从未存在过。

  • After rebasing a branch that was already pushed, the remote has commits your rewritten branch lacks → normal push rejected. git push --force (safer: --force-with-lease) overwrites the remote branch.

6.1What testing asks测试要回答什么

6.1.1Does the code do what it should?代码是否做了该做的事？★
  • Rephrased: for all valid inputs, does the code produce the intended outputs? Two sub-questions: what are the valid inputs? what behaviour is expected for them?
  • Most problems found in testing come from the programmer not knowing those answers precisely (an under-specified spec).
  • Parable of mean: "mean of an array of ints" → "…as a float" → "…and when the sum exceeds INT_MAX it should…". Each refinement is a decision a test can pin down.
  • 换个说法：对所有合法输入，代码是否产生预期输出？两个子问题：哪些输入合法？对这些输入期望什么行为？
  • 测试中发现的问题，大多源于程序员并不确切知道这些答案（规格不完整）。
  • mean 的寓言：“求 int 数组的平均值” → “……以 float 返回” → “……当总和超过 INT_MAX 时应当……”。每一步细化都是一个可以用测试固定下来的决定。

6.2Assertions断言

6.2.1assert()断言 assert()★
  • A logical statement about variables at a point in the program: "it is true that strlen(extension) > 0 here". C: #include <assert.h>.
  • If true: nothing happens. If false: the program complains (file, line, expression) and aborts — roughly if (!cond) { complain(); exit(1); }.
  • Compile with -DNDEBUG to remove all assertions (production) — the logic they guarded is then unchecked.
  • Strengths: access to internal state at runtime; test assumptions during development.
  • Limits: embedded in the code, hard to review, and don't show that the code produces the right behaviour → need an external view: Unit tests & regressions.
  • 关于程序某处变量的逻辑陈述：“此处 strlen(extension) > 0 一定成立”。C 语言：#include <assert.h>。
  • 为真：什么也不发生。为假：程序报错（文件、行号、表达式）并中止——大致相当于 if (!cond) { complain(); exit(1); }。
  • 用 -DNDEBUG 编译会移除所有断言（用于生产环境）——但它们守护的逻辑就不再被检查。
  • 优点：运行时能访问内部状态；开发时检验自己的假设。
  • 局限：嵌在代码里，难以审查；也不能证明代码产生了正确的行为 → 需要外部视角：单元测试与回归。
#include <assert.h>
static void add_mime_mapping(const char *extension, const char *mimetype) {
    assert(strlen(extension) > 0);
    assert(strlen(mimetype) > 0);
    ...
}

6.3Unit testing with Unity用 Unity 做单元测试

6.3.1Unit tests & regressions单元测试与回归★
  • Run your code against a set of inputs and compare the actual result with the declared expected result, from outside, through the code's interfaces (what users care about: does it do what the docs say?).
  • Any failing test = the current version is broken.
  • Regression: code that passed all tests before your change and fails some after — you broke previously working behaviour.
  • Frameworks exist for most languages; writing good tests is a skill (QA teams).
  • 用一组输入从外部、通过接口运行代码，把实际结果与声明的期望结果比较（这是用户关心的：它是否如文档所说？）。
  • 任何测试失败 = 当前版本有问题。
  • 回归（regression）：改动前全部测试通过，改动后有测试失败——你破坏了原本正常的行为。
  • 大多数语言都有测试框架；写好测试是一门手艺（QA 团队专做这个）。
6.3.2Unity (C test framework)Unity（C 测试框架）★
  • Unity by ThrowTheSwitch (not the game engine). Install: git clone …/Unity.git; cd Unity; cmake .; sudo make install (headers in /usr/local/include/unity/).
  • Test file includes unity.h and the code under test; defines setUp() / tearDown() (run before/after each test), test functions with assertions, and a main with UNITY_BEGIN(); RUN_TEST(test_x); return UNITY_END();.
  • Build: gcc -I /usr/local/include/unity/ -o tests test.c -l unity (-I header path, -l link library). Or export CPATH=/usr/local/include/unity/.
  • Output per test test.c:13:test_add:PASS / FAIL: Expected 0 Was 2, then a summary; exit status non-zero if any fail.
  • Assertions: TEST_ASSERT_EQUAL, TEST_ASSERT_EQUAL_FLOAT, TEST_ASSERT_EQUAL_STRING, TEST_ASSERT_TRUE… (see the Unity assertions reference).
  • ThrowTheSwitch 出品的 Unity（不是那个游戏引擎）。安装：git clone …/Unity.git; cd Unity; cmake .; sudo make install（头文件在 /usr/local/include/unity/）。
  • 测试文件包含 unity.h 和被测代码；定义 setUp() / tearDown()（每个测试前/后运行）、带断言的测试函数，以及 main：UNITY_BEGIN(); RUN_TEST(test_x); return UNITY_END();。

6.4Test-driven development测试驱动开发

6.4.1TDD: red → green → refactorTDD：红 → 绿 → 重构★
  • Bad usual process: write code → write tests → occasionally run them (by then it's already implemented the wrong way).
  • TDD: write the test for the behaviour first, then the code. Pick one specific behaviour (spec item, edge case, bug), then:
StepDo
REDwrite one test; run; confirm it currently fails
GREENmake the simplest change that passes; run; confirm pass
REFACTORmake the code good while all tests still pass
  • Keep every test → a growing test suite that documents intent and catches regressions.
  • Forces you to decide the desired output (design) before hacking. Example: test_sub fails with a copy of add ("Expected 0 Was 2") → fix → passes. Edge case add(INT_MAX, 1): decide, write the assert, then implement.
  • 常见的坏流程：写代码 → 写测试 → 偶尔跑一下（这时已经按错误的方式实现了）。
  • TDD：先为目标行为写测试，再写代码。选一个具体行为（规格条目、边界情况、bug），然后：
步骤做什么
红 RED写一个测试；运行；确认它目前失败
绿 GREEN做最简单的修改让它通过；运行；确认通过
重构 REFACTOR在所有测试仍通过的前提下把代码改好
  • 保留每一个测试 → 不断增长的测试套件，记录意图并捕获回归。
  • 迫使你在动手前先决定期望输出（设计）。例：用 add 的副本冒充 sub，test_sub 失败（“Expected 0 Was 2”）→ 修复 → 通过。边界情况 add(INT_MAX, 1)：先决定行为，写断言，再实现。

6.5Beyond example tests超越示例测试

6.5.1Property testing属性测试★
  • Spot tests check a few chosen inputs; the input space is huge. Instead, generate many random inputs and check that a property holds for all, without knowing exact outputs — e.g. a*b == b*a (commutativity).
  • QuickCheck (originally Haskell); C port quickcheck4c: QCC_testForAll(100, 1000, mulCommutativity, 2, QCC_genInt, QCC_genInt).
  • 抽样测试只检查少数挑选的输入；而输入空间巨大。改为生成大量随机输入，检查某个性质对所有输入都成立，而不必知道确切输出——如 a*b == b*a（交换律）。
  • QuickCheck（源自 Haskell）；C 版本 quickcheck4c：QCC_testForAll(100, 1000, mulCommutativity, 2, QCC_genInt, QCC_genInt)。
6.5.2Fuzzing模糊测试★
  • Fuzzers generate deranged inputs to break programs, trying to reach every path through the conditionals. Random input often makes code crash.
  • "Interesting" behaviour (unexpected path, impossible value, protected state reached) is often the first step to a vulnerability.
  • AFL taught itself valid JPEGs starting from the input "hello".
  • Lesson: "being very careful" isn't enough; you are not more inventive than fuzzer authors → need proof: Formal verification.
  • 模糊测试器生成稀奇古怪的输入来搞崩程序，试图走遍条件分支的每条路径。随机输入经常能让代码崩溃。
  • “有趣”的行为（不该走的路径、本不可能的值、访问到受保护状态）往往是发现漏洞的第一步。
  • AFL 从输入 “hello” 出发，自己摸索出了合法的 JPEG 文件。
  • 教训：“非常小心”是不够的；你不比模糊测试工具的作者更有想象力 → 需要证明：形式化验证。
6.5.3Formal verification形式化验证
  • Mathematically prove desired properties always hold under specified conditions — the highest standard of certainty.
  • Reasoning about programs in general is essentially impossible; even specific properties of constrained programs are HARD. Rare, used for high-stakes software.
  • Tools: proof assistants such as Lean (a programming language where proving correctness is part of writing the code).
  • 用数学证明在特定条件下所需性质总是成立——最高标准的确定性。
  • 对一般程序做推理基本不可能；即使只针对受限程序的特定性质也非常难。很少使用，多见于高风险软件。
  • 工具：证明助手，如 Lean（一种编程语言，证明正确性是写代码的一部分）。

8.4Normalisation规范化

8.4.1Functional dependencies函数依赖★
  • X → Y (X functionally determines Y) iff for every value of X there is at most one value of Y. E.g. StudentID → Grade (many students may share a grade). It's a feature of the process generating the data, not a coincidence of the current rows.
  • Partial dependency: a non-key attribute depends on only part of a composite key. UnitResults(*StudentID, *Unit*, Hairstyle, Grade, HairStyleRating): Hairstyle depends on StudentID alone.
  • Transitive dependency: X → Y → Z, so Z depends on X only *through* Y (Hairstyle → HairStyleRating).
  • X → Y（X 函数决定 Y）当且仅当对 X 的每个值，Y 至多有一个值。如 StudentID → Grade（多个学生可以同分）。这是产生数据的过程本身的性质，而不是当前数据碰巧如此。
  • 部分依赖：某个非键属性只依赖复合键的一部分。UnitResults(*StudentID, *Unit, Hairstyle, Grade, HairStyleRating)：Hairstyle 只依赖 StudentID。
  • 传递依赖：X → Y → Z，Z 只是*通过* Y 依赖 X（Hairstyle → HairStyleRating）。
8.4.2Normal forms 0NF → BCNF范式 0NF → BCNF★
  • Higher normal forms remove redundancy, which makes updates safe and queries easier (usually; over-normalisation has costs). 0NF > 1NF > 2NF > 3NF > BCNF > 4NF > 5NF > 6NF.
FormRequirement
0NF / UNFno duplicate records
1NF+ every attribute atomic (no lists inside a cell)
2NF+ no partial dependencies of non-key attributes on candidate keys
3NF+ no transitive dependencies of non-key attributes on candidate keys
BCNF (3.5NF)+ every attribute depends on the whole key and only the whole key (catches overlapping composite candidate keys)
4NF / 5NF / 6NFmulti-valued deps only on keys / no trivial lossless decomposition / one key + ≤1 attribute per table — rarely needed
  • Typical fix each time: extract the offending attributes into a new table and reference it with a foreign key.
  • 更高的范式消除冗余，让更新更安全、查询更方便（通常如此；过度规范化也有代价）。0NF > 1NF > 2NF > 3NF > BCNF > 4NF > 5NF > 6NF。
范式要求
0NF / UNF没有重复记录
1NF+ 每个属性都是原子的（单元格里没有列表）
2NF+ 非键属性对候选键没有部分依赖
3NF+ 非键属性对候选键没有传递依赖
BCNF（3.5NF）+ 每个属性都依赖整个键，且只依赖整个键（能抓到复合候选键重叠的情况）
4NF / 5NF / 6NF多值依赖只在键上 / 不能无损地平凡分解 / 每表一个键 + 至多一个属性——很少需要
  • 每一步的典型修法：把出问题的属性拆到新表中，再用外键引用。

9.1Types & constraints类型与约束

9.1.1SQLite type affinitySQLite 类型亲和性★
  • Most SQL engines type columns strictly and offer BOOLEAN, CHARACTER(10), DATE… SQLite is relaxed: accepts those keywords but translates/ignores them.
  • Each column has an affinity: INTEGER, TEXT, BLOB, REAL, or NUMERIC (mix); any value may be NULL. Values are converted to the preferred type when possible: INSERT INTO t1(a,b) VALUES('123',456) with a INT, b VARCHAR(10) stores 123 and '456'.
  • BOOLEAN → stored as INTEGER; CHAR/VARCHAR lengths are ignored → enforce with CHECK.
  • 多数 SQL 引擎对列类型严格，并提供 BOOLEAN、CHARACTER(10)、DATE…… SQLite 很宽松：接受这些关键字，但会转换或忽略。
  • 每列有一种亲和类型：INTEGER、TEXT、BLOB、REAL 或 NUMERIC（混合）；任何值都可以是 NULL。能转换时会转换成偏好的类型：列 a INT, b VARCHAR(10) 执行 INSERT INTO t1(a,b) VALUES('123',456) 存的是 123 和 '456'。
  • BOOLEAN → 以 INTEGER 存储；CHAR/VARCHAR 的长度被忽略 → 用CHECK约束实现。
9.1.2Constraints: CHECK, NOT NULL, UNIQUE, DEFAULT约束：CHECK、NOT NULL、UNIQUE、DEFAULT★
  • CHECK(length(shortname) <= 10) reimplements CHARACTER(10): violating inserts fail with "CHECK constraint failed".
  • CHECKs can involve several attributes: CHECK(length(shortname) <= length(name)).
  • NOT NULL forbids missing values; UNIQUE forbids duplicates; DEFAULT 1 supplies a value.
  • Constraints = the "C" (consistency) in ACID transactions.
  • CHECK(length(shortname) <= 10) 重新实现了 CHARACTER(10)：违反的插入会报 “CHECK constraint failed”。
  • CHECK 可以涉及多个属性：CHECK(length(shortname) <= length(name))。
  • NOT NULL 禁止缺失值；UNIQUE 禁止重复；DEFAULT 1 提供默认值。
  • 约束就是 ACID 事务 中的 “C”（一致性）。
CREATE TABLE degree (degreeID INTEGER UNIQUE PRIMARY KEY,
                     name TEXT NOT NULL, shortname TEXT,
                     school TEXT, durationYears INTEGER,
                     CHECK(length(shortname) <= 10));

9.3Aggregates聚合

9.3.1Aggregates & GROUP BY聚合函数与 GROUP BY★
  • Aggregate query: uses an aggregate function or GROUP BY. Functions: count(), avg(), sum(), min(), max() (count(*) counts rows; count(col) ignores NULLs).
  • Without GROUP BY the whole table is one group; a non-aggregated column then gives an ill-defined single value (SELECT avg(CustomerId), Country FROM Customer is meaningless).
  • GROUP BY col applies the aggregate within each group: SELECT count(Country), Country FROM Customer GROUP BY Country;. Several columns → cross-tabulation.
  • GROUP BY is applied after WHERE. NULLs form their own group — filter with WHERE x IS NOT NULL.
  • 聚合查询：用了聚合函数或 GROUP BY。函数：count()、avg()、sum()、min()、max()（count(*) 数行；count(列) 忽略 NULL）。
  • 没有 GROUP BY 时整张表是一个组；此时未聚合的列只给出一个含义不明的值（SELECT avg(CustomerId), Country FROM Customer 没有意义）。
  • GROUP BY 列 让聚合在每个组内计算：SELECT count(Country), Country FROM Customer GROUP BY Country;。多列分组 → 交叉统计。
  • GROUP BY 在 WHERE 之后进行。NULL 会单独成为一组——用 WHERE x IS NOT NULL 过滤。
SELECT count(CustomerId), Country, SupportRepId
FROM Customer GROUP BY SupportRepId, Country;
SELECT count(Company), Company FROM Customer
WHERE Company IS NOT NULL GROUP BY Company;
9.3.2HAVINGHAVING 分组过滤★
  • Filters groups after GROUP BY; WHERE filters rows before grouping.
  • Sometimes interchangeable (HAVING Country = 'Germany'), but conditions on aggregates need HAVING: HAVING NoCustomers > 2 — the alias doesn't exist until grouping.
  • 在 GROUP BY 之后过滤组；WHERE 在分组之前过滤行。
  • 有时二者可互换（HAVING Country = 'Germany'），但针对聚合结果的条件必须用 HAVING：HAVING NoCustomers > 2——这个别名在分组之前并不存在。
SELECT count(CustomerId) AS NoCustomers, Country, SupportRepId
FROM Customer
GROUP BY SupportRepId, Country
HAVING NoCustomers > 2;

9.5.1Sub-queries子查询★
  • Use the result of one SELECT as a temporary table for another: SELECT … FROM (SELECT … GROUP BY …); — e.g. aggregate an aggregate (albums per artist on average).

  • Stick two results together vertically: SELECT … UNION SELECT … (lab: smallest and largest ward in one table).
  • Why RIGHT JOIN in the example: keep artists with zero albums.

  • 把两个结果纵向拼起来：SELECT … UNION SELECT …（实验：最小和最大的选区放在一张表里）。
  • 例子中为什么用 RIGHT JOIN：保留专辑数为零的艺术家。

10.1Using SQL from a program在程序中使用 SQL

10.1.1Database libraries数据库接口库
  • You don't write applications in SQL: it's a domain-specific query language, not (in standard form) Turing-complete, and bad at recursion.
  • Languages provide libraries that talk to the DB engine: Python import sqlite3; Java java.sql.* + DriverManager.getConnection("jdbc:sqlite:<db>"); C sqlite3_open, sqlite3_exec.
  • 不会用 SQL 写应用程序：它是专门用于查询的领域语言，（标准形式下）不是图灵完备的，也不擅长递归。
  • 各种语言提供与数据库引擎通信的库：Python import sqlite3；Java java.sql.* + DriverManager.getConnection("jdbc:sqlite:<db>")；C 语言 sqlite3_open、sqlite3_exec。
10.1.2SQL injectionSQL 注入★
  • Appointment checker v1 builds the query from user input: sprintf(sql, "SELECT * FROM Appointment WHERE AppointmentID = %s;", appointmentID);
  • Input 1 OR 1=1 → WHERE AppointmentID = 1 OR 1=1 → always true → every appointment returned. Attackers who know SQL can read or modify the DB at will (xkcd "Bobby Tables": '); DROP TABLE Students;--).
  • Consistently in the OWASP Top Ten; estimated 10–33% of web application vulnerabilities.
  • 预约查询程序 v1 用用户输入拼出查询：sprintf(sql, "SELECT * FROM Appointment WHERE AppointmentID = %s;", appointmentID);
  • 输入 1 OR 1=1 → WHERE AppointmentID = 1 OR 1=1 → 恒为真 → 返回所有预约。懂 SQL 的攻击者可以随意读取或修改数据库（xkcd “Bobby Tables”：'); DROP TABLE Students;--）。
  • 长期位列 OWASP 十大风险；估计占 Web 应用漏洞的 10–33%。
10.1.3Prepared statements预编译语句（参数化查询）★
  • The fix: write the query with placeholders ?, let the library prepare it, then bind user input as values. Input can no longer be parsed as SQL clauses.
  • Effect: 1 OR 1=1 is treated like WHERE AppointmentID = '1 OR 1=1' (a value, matches nothing).
  • Always use your DB library's prepared-statement API for user input.
  • 修复方法：用占位符 ? 写查询，让库先预编译，再把用户输入作为值绑定进去。输入再也不会被解析成 SQL 子句。
  • 效果：1 OR 1=1 相当于 WHERE AppointmentID = '1 OR 1=1'（只是一个值，什么也匹配不到）。
  • 处理用户输入时，一律使用数据库库提供的预编译语句接口。
sqlite3_stmt *stmt;
char *sql = "SELECT * FROM Appointment WHERE AppointmentID = ?";
retval = sqlite3_prepare_v2(db, sql, -1, &stmt, 0);
if (retval == SQLITE_OK)
    sqlite3_bind_text(stmt, 1, appointmentID, strlen(appointmentID), SQLITE_STATIC);
while (sqlite3_step(stmt) == SQLITE_ROW) { /* read columns */ }
sqlite3_finalize(stmt);

10.2.2Recursive data structures递归数据结构
  • Trees and graphs are efficient representations for: organisational hierarchies, file storage, process relationships.
  • Storable in relational tables, but hard to query to arbitrary depth.
  • What we want is simple: Y manages X if X reports directly to Y, or Y manages whoever X reports to → a recursive rule (Recursive rules).
  • 树和图是这些问题的高效表示：组织层级、文件存储、进程关系。
  • 可以存进关系表，但很难查询任意深度。
  • 我们想要的其实很简单：若 X 直接向 Y 汇报，或者 Y 管理 X 的直接上级，则 Y 管理 X → 一条递归规则（递归规则）。
manages(Y, X) :- directreport(Y, X).
manages(Y, X) :- directreport(Z, X), manages(Y, Z).
10.2.3WITH RECURSIVE (bonus)WITH RECURSIVE 递归查询（补充）
  • SQL's escape hatch (file recurse.sql in the lecture folder): a recursive common table expression = base query UNION a step that joins the table with the CTE itself, repeated until no new rows.
  • SQL 的“后门”（讲义目录中的 recurse.sql）：递归公用表表达式 = 基础查询 UNION 一个把原表与该 CTE 自身连接的步骤，反复执行直到不再产生新行。
WITH RECURSIVE mymanagers(m) AS (
  SELECT manager FROM manager WHERE employee = 'Matthew Edwards'
  UNION
  SELECT manager FROM manager, mymanagers WHERE manager.employee = mymanagers.m)
SELECT * FROM mymanagers;
