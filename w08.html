8.1

Why storage decisions matter为什么存储决策很重要

Why not a spreadsheet: real failures, and the ACID guarantees we need.为什么不用电子表格：真实的失败案例，以及我们需要的 ACID 保证。

#Bad data storage has victims糟糕的数据存储会害人exam focus重点

  • Engineers are responsible for what they build (the Calling of the Engineer, after the Quebec Bridge disaster: 75 deaths).
  • UK COVID track-and-trace used the old .xls format: max 65,536 rows; extra cases silently dropped. 15,841 referrals missed → est. 125,000–185,000 extra infections, 1,500–2,500 extra deaths (system cost £35m).
  • Genomics: Excel auto-converts gene names (SEPT2 → 2-September, 2310009E13 → 2.31E+13); ~1 in 5 genome datasets affected (2016), rising.
  • Building your own storage from scratch ≈ writing your own crypto library: don't. Use a database.
  • 工程师要为自己的作品负责（“工程师召唤”仪式，源于魁北克大桥事故：75 人死亡）。
  • 英国新冠追踪系统用旧 .xls 格式：最多 65,536 行，超出的病例被悄悄丢弃。漏掉 15,841 个转介 → 估计多出 125,000–185,000 例感染、1,500–2,500 人死亡（系统花费 3500 万英镑）。
  • 基因组学：Excel 自动转换基因名（SEPT2 → 9 月 2 日，2310009E13 → 2.31E+13）；2016 年约五分之一基因数据集受影响，且比例上升。
  • 自己从零造存储系统 ≈ 自己写加密库：别这么做。用数据库。

#ACID transactionsACID 事务exam focus重点

  • If multiple applications/people/processes read and write the data, use a database engine that provides ACID transactions (MySQL, MariaDB…). An update must be:

Aatomiccompletes entirely or not at all
Cconsistentall constraints of the design are respected
Iisolateddoesn't interfere with other concurrent updates
Ddurablewritten to persistent storage
  • Without concurrency needs you may still want a relational system: SQLite, DuckDB. In SQL: Transactions.
  • 若有多个应用/人/进程同时读写数据，就要用提供 ACID 事务的数据库引擎（MySQL、MariaDB……）。一次更新必须：
字母性质含义
A原子性 atomic要么全部完成，要么完全没发生
C一致性 consistent遵守设计中的所有约束
I隔离性 isolated不影响其他并发更新
D持久性 durable写入持久存储
  • 不需要并发保证时，也可能需要关系型系统：SQLite、DuckDB。在 SQL 中：事务。

8.2

The relational model关系模型

Model the world as tables of entities linked by relationships.把世界建模为由联系连接起来的实体表。

#Entities, attributes, records实体、属性、记录exam focus重点

ConceptExampleIn a relational DB
entity (type of thing)Student, Building, Eventa table
attributename, address, capacitya column
record (instance)'MVB', Woodland Rd, 400a row
relationshipstudent *studies in* buildingcolumns that refer to other tables (Foreign keys)
  • "Relational": tables have columns that reference rows of other tables. How to identify a row? Not "the 4th row" (order changes, rows deleted) → Keys: candidate, composite, surrogate, primary.
概念例子在关系数据库中
实体（一类事物）学生、建筑、活动一张表
属性名称、地址、容量一列
记录（实例）'MVB'、Woodland Rd、400一行
联系学生*在*某建筑上课引用其他表的列（外键）
  • “关系型”：表中的列引用其他表的行。怎样标识一行？不能用“第 4 行”（顺序会变、行会被删）→ 键：候选键、复合键、代理键、主键。

#ER diagrams & cardinalityER 图与基数exam focus重点

  • Entity-relationship diagram: tables as boxes with attributes; relationships as lines whose ends show cardinality (one / many) and whether they are mandatory or optional. Tools: pen and paper, draw.io ("Entity Relation" section).
RelationshipImplement as
one-to-oneFK on either side (usually the optional side), UNIQUE
one-to-manyFK on the many side (e.g. Lecturer → ResearchGroup FK is on Lecturer)
many-to-manya separate join table holding two FKs (e.g. Enrolment(student, unit))
  • Lab: HovSoc (members, committee roles, events with organiser & attendees); university marks (actual vs agreed mark after the exam board). Key rule: store each fact once — otherwise updates leave contradictions.
  • 实体-联系图：表画成带属性的方框；联系画成连线，两端标明基数（一 / 多）以及是必选还是可选。工具：纸笔、draw.io（“Entity Relation” 分类）。
联系实现方式
一对一外键放任一侧（通常放可选一侧），加 UNIQUE
一对多外键放在多的一侧（如“讲师属于研究组”，外键在 Lecturer 表）
多对多单独的连接表，存两个外键（如 Enrolment(student, unit)）
  • 实验：HovSoc 社团（成员、委员会职位、带组织者和参与者的活动）；大学成绩（考试委员会前的原始分与确认分）。核心原则：每个事实只存一次——否则更新时会产生矛盾。

Keys键

To link rows you must identify them → keys.要连接行，就得先唯一标识行 → 键。

#Keys: candidate, composite, surrogate, primary键：候选键、复合键、代理键、主键exam focus重点

  • A key = a combination of attributes that uniquely identifies a row.
TermMeaning
candidate keya minimal set of attributes that uniquely identifies records (one of possibly several)
composite keya key made of more than one attribute (e.g. Location + Time)
surrogate keyan attribute invented only to be a key (Transaction ID, DegreeID)
primary keythe key you actually chose for the table
foreign keya primary key of one table used as a reference in another (Foreign keys)
  • 键 = 能唯一标识一行的属性组合。
术语含义
候选键 candidate key能唯一标识记录的最小属性集（可能有多个）
复合键 composite key由多于一个属性组成的键（如 地点 + 时间）
代理键 surrogate key专门为了做键而创造的属性（交易号、DegreeID）
主键 primary key表实际选用的那个键
外键 foreign key某表的主键在另一表中作为引用（外键）

8.4

Normalisation规范化

Keys reveal dependencies → split tables to remove redundancy.键揭示依赖 → 拆分表以消除冗余。

#Functional dependencies函数依赖exam focus重点

  • X → Y (X functionally determines Y) iff for every value of X there is at most one value of Y. E.g. StudentID → Grade (many students may share a grade). It's a feature of the process generating the data, not a coincidence of the current rows.
  • Partial dependency: a non-key attribute depends on only part of a composite key. UnitResults(*StudentID, *Unit*, Hairstyle, Grade, HairStyleRating): Hairstyle depends on StudentID alone.
  • Transitive dependency: X → Y → Z, so Z depends on X only *through* Y (Hairstyle → HairStyleRating).
  • X → Y（X 函数决定 Y）当且仅当对 X 的每个值，Y 至多有一个值。如 StudentID → Grade（多个学生可以同分）。这是产生数据的过程本身的性质，而不是当前数据碰巧如此。
  • 部分依赖：某个非键属性只依赖复合键的一部分。UnitResults(*StudentID, *Unit, Hairstyle, Grade, HairStyleRating)：Hairstyle 只依赖 StudentID。
  • 传递依赖：X → Y → Z，Z 只是*通过* Y 依赖 X（Hairstyle → HairStyleRating）。
See also相关Normal forms 0NF → BCNF范式 0NF → BCNFKeys: candidate, composite, surrogate, primary键：候选键、复合键、代理键、主键

#Normal forms 0NF → BCNF范式 0NF → BCNFexam focus重点

  • Higher normal forms remove redundancy, which makes updates safe and queries easier (usually; over-normalisation has costs). 0NF > 1NF > 2NF > 3NF > BCNF > 4NF > 5NF > 6NF.
FormRequirement
0NF / UNFno duplicate records
1NF+ every attribute atomic (no lists inside a cell)
2NF+ no partial dependencies of non-key attributes on candidate keys
3NF+ no transitive dependencies of non-key attributes on candidate keys
BCNF (3.5NF)+ every attribute depends on the whole key and only the whole key (catches overlapping composite candidate keys)
4NF / 5NF / 6NFmulti-valued deps only on keys / no trivial lossless decomposition / one key + ≤1 attribute per table — rarely needed
  • Typical fix each time: extract the offending attributes into a new table and reference it with a foreign key.
  • 更高的范式消除冗余，让更新更安全、查询更方便（通常如此；过度规范化也有代价）。0NF > 1NF > 2NF > 3NF > BCNF > 4NF > 5NF > 6NF。
范式要求
0NF / UNF没有重复记录
1NF+ 每个属性都是原子的（单元格里没有列表）
2NF+ 非键属性对候选键没有部分依赖
3NF+ 非键属性对候选键没有传递依赖
BCNF（3.5NF）+ 每个属性都依赖整个键，且只依赖整个键（能抓到复合候选键重叠的情况）
4NF / 5NF / 6NF多值依赖只在键上 / 不能无损地平凡分解 / 每表一个键 + 至多一个属性——很少需要
  • 每一步的典型修法：把出问题的属性拆到新表中，再用外键引用。

#Worked example: the Event table实例：Event 表逐步规范化exam focus重点

  • Start (0NF): Event(*Location, *Time, Organiser, OrganiserEmail, Attendees, SafetyOfficer, Name) with Attendees = "jay; rob; mary".
StepProblemFix
0NF → 1NFAttendees is a list (not atomic)new table EventAttendances(Attendee, EventLoc, EventTime), FK → Event
1NF → 2NFSafetyOfficer depends only on Location (part of the key)new table LocationSafety(*Location, SafetyOfficer)
2NF → 3NFOrganiser depends on OrganiserEmail (transitive)new table Organiser(*OrganiserEmail, Name); keep OrganiserEmail in Event as FK
3NFEvent(*Location, *Time, OrganiserEmail, Name)also BCNF: only dependency is on the candidate key
  • Win: Rob Money's name is no longer repeated; "which events did jay attend?" is a lookup, not a text search.
  • 起点（0NF）：Event(*Location, *Time, Organiser, OrganiserEmail, Attendees, SafetyOfficer, Name)，其中 Attendees = "jay; rob; mary"。
步骤问题修法
0NF → 1NFAttendees 是列表（不原子）新表 EventAttendances(Attendee, EventLoc, EventTime)，外键 → Event
1NF → 2NFSafetyOfficer 只依赖 Location（键的一部分）新表 LocationSafety(*Location, SafetyOfficer)
2NF → 3NFOrganiser 依赖 OrganiserEmail（传递依赖）新表 Organiser(*OrganiserEmail, Name)；Event 中保留 OrganiserEmail 作外键
3NFEvent(*Location, *Time, OrganiserEmail, Name)同时满足 BCNF：唯一的依赖就是对候选键的依赖
  • 好处：Rob Money 的名字不再重复出现；“jay 参加过哪些活动？”变成查表，而不是文本搜索。

Creating tables in SQLite在 SQLite 中建表

Write the design down as SQL tables.把设计写成 SQL 表。

#The sqlite3 shellsqlite3 命令行

  • sqlite3 test.db opens (creates) a database file; sqlite3 alone = temporary in-memory DB.
  • Dot-commands (not SQL): .tables, .schema [table], .headers on, .mode column, .quit. Also ATTACH DATABASE 'x.db' AS x;.
  • Run a script: sqlite3 test.db < myscript.sql (without a file name nothing persists).
  • Convention: CAPITALISE SQL keywords; statements end with ;.
  • sqlite3 test.db 打开（或新建）数据库文件；只写 sqlite3 = 临时的内存数据库。
  • 点命令（不是 SQL）：.tables、.schema [表]、.headers on、.mode column、.quit。还有 ATTACH DATABASE 'x.db' AS x;。
  • 运行脚本：sqlite3 test.db < myscript.sql（不给文件名则不会持久保存）。
  • 约定：SQL 关键字大写；语句以 ; 结尾。
See also相关CREATE TABLECREATE TABLE 建表W2Redirection重定向

#CREATE TABLECREATE TABLE 建表exam focus重点

  • Columns with types and constraints; PRIMARY KEY on a column, or PRIMARY KEY(a, b) at the end for a composite key.
  • FOREIGN KEY(col) REFERENCES other(col) must be declared at creation → create the referenced table first.
  • Turn on enforcement: PRAGMA foreign_keys = ON; (then inserting a non-existent degree fails).
  • CREATE/DROP script: start with DROP TABLE IF EXISTS t; lines in the reverse of creation order (drop referencing tables first), then the CREATEs → re-running always gives fresh empty tables.
  • 列带类型和约束；PRIMARY KEY 写在列后，或在末尾写 PRIMARY KEY(a, b) 定义复合主键。
  • FOREIGN KEY(列) REFERENCES 另一表(列) 必须在建表时声明 → 先建被引用的表。
  • 开启外键检查：PRAGMA foreign_keys = ON;（之后插入不存在的专业号会失败）。
  • 建表/删表脚本：先按建表相反顺序写 DROP TABLE IF EXISTS t;（先删引用别人的表），再写各个 CREATE → 每次重跑都得到全新的空表。
PRAGMA foreign_keys = ON;
DROP TABLE IF EXISTS student;
DROP TABLE IF EXISTS degree;
CREATE TABLE degree (degreeID INTEGER UNIQUE PRIMARY KEY,
                     name TEXT, school TEXT, durationYears INTEGER);
CREATE TABLE student (studentNo INTEGER UNIQUE PRIMARY KEY,
                      name TEXT, feeStatus TEXT, studies INTEGER,
                      FOREIGN KEY(studies) REFERENCES degree(degreeID));

#INSERT INTOINSERT INTO 插入exam focus重点

  • INSERT INTO degree VALUES (1001, 'Computer Science', 'COMS', 3); — values in column order. Name columns explicitly: INSERT INTO t(a, b) VALUES (…).
  • Several rows at once: VALUES (…), (…), (…);.
  • Inserting a row whose primary key already exists fails (UNIQUE constraint) — why running the single inserts *and then* the multi-row insert fails.
  • Check: SELECT * FROM degree;.
  • INSERT INTO degree VALUES (1001, 'Computer Science', 'COMS', 3);——按列顺序给值。也可显式指定列：INSERT INTO t(a, b) VALUES (…)。
  • 一次插入多行：VALUES (…), (…), (…);。
  • 插入主键已存在的行会失败（UNIQUE 约束）——这就是先逐条插入、*再*执行多行插入会失败的原因。
  • 检查：SELECT * FROM degree;。

Exam checklist考点速记

  • ACID = Atomic, Consistent, Isolated, Durable.
  • Entity → table, attribute → column, record → row; relationships via foreign keys.
  • Keys: candidate (minimal unique set), composite (>1 attribute), surrogate (invented ID), primary (chosen), foreign (another table's PK).
  • X → Y: each X has at most one Y. Partial dependency (on part of a composite key) and transitive dependency (X→Y→Z).
  • 1NF atomic values; 2NF no partial deps; 3NF no transitive deps; BCNF every determinant is a candidate key.
  • CREATE TABLE … PRIMARY KEY … FOREIGN KEY(x) REFERENCES t(y); PRAGMA foreign_keys = ON;; create referenced table first, drop in reverse order.
  • ACID = 原子性、一致性、隔离性、持久性。
  • 实体 → 表，属性 → 列，记录 → 行；联系通过外键表示。
  • 键：候选键（最小唯一属性集）、复合键（多于一个属性）、代理键（人为编号）、主键（选定的）、外键（引用另一表的主键）。
  • X → Y：每个 X 最多对应一个 Y。部分依赖（依赖复合键的一部分）与传递依赖（X→Y→Z）。
  • 1NF 值原子；2NF 无部分依赖；3NF 无传递依赖；BCNF 每个决定因素都是候选键。
  • CREATE TABLE … PRIMARY KEY … FOREIGN KEY(x) REFERENCES t(y)；PRAGMA foreign_keys = ON;；先建被引用表，删除时顺序相反。
